# 데이터 분석 조직 커밋 메시지 컨벤션

Conventional Commits 1.0 (`<type>(<scope>): <subject>`)을 뼈대로 하되, 데이터 분석 조직의
산출물(분석 스크립트, 노트북, 결과 데이터, 리포트, 모델)에 맞게 type·scope·본문 규칙을 조정했다.
기존 이력(`feat: 노선별·시간대별 혼잡도 분석 스크립트 및 결과 CSV 추가`)과 호환된다.

## 목차
1. 메시지 구조
2. type 표
3. scope 규칙
4. subject 작성 규칙
5. body / footer 규칙 (데이터 조직 특화)
6. 커밋 분리·묶음 기준
7. 커밋하면 안 되는 것
8. 예시
9. 브랜치 병합 커밋

## 1. 메시지 구조

```
<type>(<scope>): <subject>        ← 필수, 한 줄

<body>                            ← 선택, 빈 줄 후 작성. "왜/무엇을/주의점"

<footer>                          ← 선택. 이슈 참조, BREAKING CHANGE, 데이터 트레일러
```

scope는 생략 가능하다 (`feat: ...`). 저장소에 분석 영역이 하나뿐이거나 변경이 여러 영역에 걸치면 생략한다.

## 2. type 표

| type | 사용 시점 | 데이터 조직에서의 예 |
| --- | --- | --- |
| `feat` | 새 분석·지표·파이프라인·기능 추가 | 혼잡도 분석 스크립트 신규, 신규 KPI 산출 |
| `fix` | 계산·쿼리·조인·필터의 **결과가 틀린** 문제 수정 | 환승 판정 시간 기준 오류, 조인 중복으로 행 뻥튀기 |
| `data` | 데이터셋·참조 테이블·분석 결과 산출물(CSV 등)·더미/샘플 데이터 추가·갱신 | 정류장 마스터 갱신, 월별 결과 CSV 재산출 |
| `report` | 리포트·대시보드·시각화·발표 자료 | 노선별 혼잡도 차트, 주간 리포트 노트북 |
| `model` | 모델·피처·학습/평가 로직 | 수요 예측 피처 추가, 하이퍼파라미터 조정 |
| `refactor` | 결과는 같고 구조만 개선 | 중복 전처리 함수화, 변수명 정리 |
| `perf` | 결과는 같고 속도·메모리 개선 | 반복문 → 벡터 연산, 쿼리 인덱스 활용 |
| `test` | 테스트·데이터 검증(assert, great_expectations 등) 추가·수정 | 스키마/결측 검증 추가 |
| `docs` | 문서·주석·README·데이터 사전 | 컬럼 정의서, 지표 산식 설명 |
| `build` | 의존성·환경 | requirements.txt, environment.yml, pyproject |
| `ci` | CI/CD, 스케줄러, 배치 정의 | GitHub Actions, Airflow DAG 설정 |
| `chore` | 위에 안 맞는 잡무 | .gitignore, 폴더 이동, 설정 파일 |
| `revert` | 이전 커밋 되돌리기 | `revert: "feat: ..." 되돌림` + 원래 해시 |

### 헷갈리기 쉬운 경계

- **분석 스크립트 + 그 스크립트가 만든 결과 CSV** → 하나의 `feat`. 결과는 스크립트에서 재생성되는 부산물이므로 따로 쪼개지 않는다.
- **스크립트는 그대로, 결과만 다시 산출** → `data`.
- **계산식을 바꿔 결과 수치가 달라짐** → 기존 로직의 오류 수정이면 `fix`, 의도된 정의 변경이면 `feat`. 어느 쪽이든 `Metric-Change:` 트레일러를 붙인다 (5번 참고).
- **결과가 같은데 코드만 정리** → `refactor`. 결과 diff가 있다면 refactor가 아니다.
- **노트북 셀 출력만 갱신** → `report`(공유용 노트북) 또는 `chore`(출력 정리). 출력은 가급적 비운 채 커밋한다.

## 3. scope 규칙

scope는 "무엇에 대한 변경인가"를 나타내는 짧은 영문 소문자 명사(하이픈 허용)다. 우선순위:

1. **분석 주제/도메인**: 파일명에서 추출한다. `analyze_od.py` → `od`, `analyze_fare.py` → `fare`.
   기존 이력과 브랜치명(`feature/congestion`)이 이 방식이므로 그대로 이어 간다.
2. **파이프라인 단계**: `etl`, `ingest`, `features`, `eval`, `viz` 등 (도메인으로 특정할 수 없을 때).
3. **공통 영역**: `deps`, `docs`, `config`, `data-dict`.

한 커밋 안의 파일이 여러 도메인에 걸치면 scope를 생략한다. scope를 `a,b`처럼 나열하지 않는다
(나열해야 한다면 커밋을 나눌 신호다).

## 4. subject 작성 규칙

- **언어**: 한국어. 기술 용어·파일명·지표명은 원어 그대로 (`OD`, `pandas`, `analyze_od.py`).
- **길이**: 제목 전체(`type(scope): ` 포함) 50자 안팎, 최대 72자.
- **어미**: 명사형 종결. `추가`, `수정`, `개선`, `제거`, `변경`, `분리`. (`추가함`, `추가했다`, `추가한다` 지양)
- **마침표 없음**.
- **무엇이 아니라 의미를 쓴다**: "코드 수정" ✗ → "환승 판정 기준을 30분에서 20분으로 변경" ✓.
- 한 줄에 `및`이 두 번 이상 나오면 둘 이상의 변경이 섞인 것이니 커밋을 나눌 수 있는지 먼저 본다.
  (스크립트 및 결과 CSV 처럼 한 번 쓰는 것은 괜찮다.)

## 5. body / footer 규칙 (데이터 조직 특화)

body는 diff를 읽으면 알 수 있는 "무엇"을 반복하지 않고, **diff로 알 수 없는 맥락**을 적는다.
간단한 변경(제목만으로 충분한 경우)은 body를 생략한다. 아래에 해당하면 body를 반드시 쓴다.

| 상황 | body에 적을 것 |
| --- | --- |
| 새 분석·지표 | 분석 목적, 지표 정의/산식, 집계 단위(노선×시간대 등) |
| 결과가 바뀌는 수정 | 수정 전/후 수치 차이(예: 환승률 12.4% → 9.8%), 영향 범위, 원인 |
| 데이터 갱신 | 출처, 기간, 행 수(전/후), 스키마 변경 여부 |
| 필터·제외 조건 | 제외한 대상과 건수·비율, 제외 사유 |
| 가정·한계 | 추정 로직(환승 추정 등)의 가정, 알려진 한계 |
| 모델 변경 | 평가 지표 전/후 비교, 학습 데이터 기간 |

형식은 `-` 불릿으로 3~6줄 이내, 한 줄 72자 안팎으로 줄바꿈한다.

### footer 트레일러

필요할 때만 쓴다. 값은 실제 확인된 것만 적고 모르면 줄 자체를 생략한다 (추측 금지).

```
Data-Source: card_taps.xlsx (sheet: tap_log)
Data-Period: 2024-01-01 ~ 2024-01-31
Rows: 12,000 -> 11,874
Metric-Change: 환승률 산식 변경 (결과 수치 변동 있음)
Refs: #123
BREAKING CHANGE: 결과 CSV의 컬럼명 route -> route_id
```

- `Metric-Change:` — 지표 정의가 바뀌어 **과거 수치와 직접 비교할 수 없을 때** 반드시 붙인다.
  분석 조직에서는 코드 버그보다 "숫자가 왜 달라졌지?"가 훨씬 비싼 질문이기 때문이다.
- `BREAKING CHANGE:` — 결과 파일의 컬럼/스키마/경로 변경처럼 하위 소비자(대시보드, 다른 분석)가 깨질 수 있을 때. type 뒤에 `!`를 붙여도 된다 (`fix(fare)!: ...`).
- `Refs:` — 이슈/티켓/요청 번호.

## 6. 커밋 분리·묶음 기준

**하나의 커밋 = 하나의 논리적 변경.** 리뷰어가 "이 커밋은 한 문장으로 설명된다"고 느껴야 한다.

묶는다:
- 같은 분석 주제의 스크립트 + 그 결과물 (`analyze_od.py` + `results/od_*.csv`)
- 같은 목적의 코드 + 그 코드를 위한 테스트/검증
- 같은 지표를 설명하는 코드 변경 + 데이터 사전/README 변경 (문서가 코드에 종속될 때)

나눈다:
- 서로 다른 분석 주제 (`od` vs `fare`)
- 기능 추가와 리팩터링 (되돌리기·리뷰·bisect를 위해)
- 지표 정의 변경(`fix`/`feat`)과 단순 정리(`refactor`)
- 의존성(`build`), 설정(`chore`), 독립 문서(`docs`) 변경
- 결과가 바뀌는 변경과 결과를 바꾸지 않는 변경

같은 파일 안에 성격이 다른 변경이 섞여 있으면 `git add -p`로 hunk 단위로 나눌 수 있다.
다만 나누는 이유가 분명하지 않으면 과분할하지 않는다. 파일 한두 개 변경에 커밋 다섯 개는 노이즈다.

## 7. 커밋하면 안 되는 것 (발견하면 사용자에게 알린다)

- **개인정보·민감정보**: 이름, 전화번호, 카드번호, 계정 ID가 원본 그대로 든 데이터. 비식별화 여부를 확인한다.
- **원본/대용량 데이터**: 대략 10MB 이상, 또는 `.parquet`, `.xlsx`, `.csv` 원본 덤프. 재생성 가능하면 `.gitignore` 처리하고 생성 스크립트만 커밋한다 (이 저장소의 `data/*.xlsx` 방식).
- **자격 증명**: `.env`, API 키, DB 접속 문자열, 토큰.
- **노트북 실행 출력**: 출력 셀에 실제 데이터가 노출될 수 있다. 출력을 비우고 커밋하도록 권한다.
- **임시·캐시 파일**: `__pycache__`, `.ipynb_checkpoints`, Excel 잠금파일(`~$*.xlsx`).

## 8. 예시

```
feat(congestion): 노선별·시간대별 혼잡도 분석 스크립트 및 결과 CSV 추가

- 집계 단위: 노선 × 시간대(1시간), 지표: 탑승 건수 / 정원 대비 비율
- 정원은 bus_routes.xlsx의 capacity 컬럼 기준

Data-Source: card_taps.xlsx (sheet: tap_log)
```

```
fix(transfer): 환승 판정 시 하차-승차 시간차 부호 오류 수정

- 승차 시각이 하차 시각보다 빠른 음수 시간차가 환승으로 집계되던 문제
- 환승률 12.4% -> 9.8%로 감소

Metric-Change: 환승률 (과거 수치와 직접 비교 불가)
```

```
data: 더미 교통카드 데이터 재생성 (12,000건 -> 50,000건)

- 시드 고정(seed=42), 생성 스크립트 변경 없음
Rows: 12,000 -> 50,000
```

```
refactor(od): 정류장 매핑 로직을 함수로 분리

결과 CSV 변동 없음 (diff 확인).
```

```
build: pandas 2.2로 업그레이드, openpyxl 추가
```

```
docs: 컬럼 정의서(data dictionary)에 환승 판정 기준 추가
```

## 9. 브랜치 병합 커밋

`git merge`가 만드는 커밋은 `merge: <브랜치명> <요약>` 형태를 따른다 (기존 이력:
`merge: feature/fare 분석 추가`). 이 스킬은 보통 일반 변경 커밋을 다루므로 병합 커밋은
사용자가 요청할 때만 작성한다.
