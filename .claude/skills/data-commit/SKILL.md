# data-commit: 데이터 분석 조직 커밋 스킬

변경 파일을 읽고 → 비슷한 것끼리 묶고 → 컨벤션에 맞는 메시지를 쓴다.
분석 조직에서 커밋 이력은 "이 숫자가 언제, 왜 바뀌었나"를 추적하는 감사 기록이기도 하다.
그래서 이 스킬은 메시지 형식만이 아니라 **묶음의 단위**와 **결과가 바뀌었는지 여부의 기록**에 무게를 둔다.

컨벤션 전문(type 표, scope 규칙, body/트레일러 규칙, 예시)은 `references/convention.md`에 있다.
메시지를 쓰기 전에 읽는다. 아래는 작업 순서와 판단 요령이다.

## 작업 순서

### 1. 변경 사항 수집

```bash
python .claude/skills/data-commit/scripts/collect_changes.py
```

스크립트는 `git status`와 `numstat`을 읽어 파일을 종류(code / result / data / notebook / deps / doc / config …)로
분류하고, 분석 주제(`analyze_od.py` ↔ `results/od_*.csv`)별 후보 그룹과 주의사항(대용량, 자격 증명 의심,
노트북 출력, 신규 데이터 파일)을 출력한다. 이 출력은 **초안**이다. 파일명 규칙에 의존하므로 틀릴 수 있다.

변경이 없으면 그렇게 알리고 끝낸다. 이미 스테이징된 파일이 있으면 사용자가 의도해서 올려둔 것일 수 있으니,
기존 스테이징을 임의로 되돌리지 말고 그 존재를 알리고 어떻게 할지 묻는다.

### 2. diff를 읽고 그룹 확정

경로만 보고 type을 정하면 틀린다. 각 그룹의 `git diff`(신규 파일은 내용 앞부분)를 읽고 다음을 판단한다.

- **결과가 바뀌는가?** 계산식·조인·필터·집계 단위가 바뀌면 결과 수치가 달라진다 → `fix`/`feat` + 지표 변경 기록.
  결과가 같다면 `refactor`/`perf`. 확신이 없으면 스크립트를 다시 돌려 결과 CSV diff로 확인할 수 있는지 먼저 본다.
- **무엇을 위한 변경인가?** (새 분석 / 버그 / 데이터 갱신 / 정리) — 이것이 type을 결정한다.
- **한 파일에 성격이 다른 변경이 섞였는가?** 섞였다면 `git add -p`로 hunk를 나눌 수 있는지 검토한다.
  단, 과분할은 노이즈이므로 나누는 이유가 분명할 때만 한다.

묶음 원칙은 "커밋 하나가 한 문장으로 설명되는가"다. 같은 분석의 스크립트와 그 결과물은 한 커밋으로,
서로 다른 분석 주제·기능 추가 vs 리팩터링·의존성/설정/독립 문서는 따로 나눈다 (`references/convention.md` 6번).

### 3. 위험 파일 점검

스크립트 경고와 diff를 보고, 커밋하면 안 되는 것(개인정보가 든 원본 데이터, 자격 증명, 대용량 덤프,
출력이 남은 노트북, 캐시 파일)이 있으면 **해당 파일을 커밋 계획에서 빼고** 사용자에게 알린다.
한번 커밋된 데이터는 이력에서 지우기 어렵기 때문에, 애매하면 넣지 말고 묻는 쪽이 안전하다.

### 4. 메시지 작성

`references/convention.md` 규칙대로 쓴다. 핵심만 요약하면:

- `type(scope): 한국어 명사형 subject` — 50자 안팎, 마침표 없음. scope는 분석 주제(파일명 기준) 우선.
- body는 diff로 알 수 없는 맥락(지표 정의, 수정 전/후 수치, 데이터 기간·행 수, 제외 조건, 가정)만 쓴다.
  새 분석·결과가 바뀌는 수정·데이터 갱신이면 body를 쓰고, 단순 변경이면 제목만으로 끝낸다.
- 트레일러(`Data-Source`, `Data-Period`, `Rows`, `Metric-Change`, `BREAKING CHANGE`)는 **확인된 사실만** 적는다.
  수치를 지어내지 않는다. 코드·데이터에서 읽을 수 있으면 읽어서 쓰고(행 수는 파일을 열어 확인 가능),
  알 수 없으면 줄을 생략하거나 사용자에게 묻는다. 틀린 수치가 적힌 커밋 메시지는 없는 것보다 해롭다.
- 이 저장소의 기존 이력 형식(`feat: ... 추가`)과 어긋나지 않게 한다.

### 5. 계획 제시 → 확인 → 커밋

커밋은 되돌리기 번거로운 동작이므로, 실행 전에 아래 형식으로 계획을 보여주고 승인을 받는다.
사용자가 "알아서 커밋해"처럼 이미 승인했다면 바로 진행한다.

```
커밋 1/3  feat(od): 정류장 OD 분석 스크립트 및 결과 CSV 추가
  - analyze_od.py
  - results/od_matrix.csv
  - results/od_top10.csv
  (본문/트레일러가 있으면 함께 표시)

커밋 2/3  build: openpyxl 의존성 추가
  - requirements.txt

제외: .env (자격 증명 의심), __pycache__/ (캐시)
```

승인 후 커밋마다 **파일을 명시해서** 스테이징한다 (`git add .`, `git add -A` 금지 — 다른 그룹이나
제외한 파일이 딸려 들어가기 때문).

```bash
git add analyze_od.py results/od_matrix.csv results/od_top10.csv
git commit -F - <<'EOF'
feat(od): 정류장 OD 분석 스크립트 및 결과 CSV 추가

- 집계 단위: 승차 정류장 × 하차 정류장

Data-Source: card_taps.xlsx (sheet: tap_log)
EOF
```

멀티라인 메시지는 `-m` 여러 번보다 heredoc(`-F -`)이 줄바꿈·한글 처리에 안전하다.
이 환경(Windows)에서 PowerShell을 쓸 때는 here-string(`@' ... '@`)을 `git commit -F -`에 파이프한다.
커밋 메시지 끝의 공동 작성자(Co-Authored-By) 표기는 세션/프로젝트가 요구하는 대로 따른다.

마지막으로 `git log --oneline -n <커밋 수>`와 `git status`로 결과를 보여준다.
훅이 실패하면 `--no-verify`로 우회하지 말고 원인을 고쳐 새로 커밋한다. push는 요청받았을 때만 한다.

## 범위 밖

- 병합 커밋(`merge:`)은 사용자가 요청할 때만 쓴다 (`references/convention.md` 9번).
- 이미 만든 커밋의 메시지 수정(`--amend`, rebase)은 이력을 바꾸므로 사용자가 명시적으로 요청할 때만 한다.
  push된 커밋이면 먼저 경고한다.
